    15. CuTe — Layout Algebra You Can Check by Hand¶

    Chapter 15 Companion Guide — From Address Arithmetic to CuTe Foundations¶

    Your goal in this chapter

    Read a CuTe layout as an address function and distinguish a view from a transfer. Begin with ordinary array indexing, element sizes and row strides; the numbered calculations below build the CuTe vocabulary from those facts. The earlier shared-memory layout and WGMMA fragments chapters become useful again when Chapters 20–22 connect these maps to actual instructions.

    1 — The missing bridge to library kernels¶

    A hand-written kernel often hides its layout in arithmetic: m * leading_dimension + n, a swizzle XOR, or a lane-dependent register index. CuTe makes such mappings explicit types and objects. That lets CUTLASS describe global tiles, shared-memory stages, copy ownership and MMA fragments using related operations instead of unrelated indexing formulas.

    This chapter covers the C++ CuTe API distributed with CUTLASS v4.3.6, pinned by the workspace setup below. CuTe’s Python DSL is a separate programming interface; do not mix its examples, imports or JIT rules with these C++ headers. Newer releases can add schedules and change builders, so this is a reproducible reading baseline rather than a claim that v4.3.6 is the latest release.

    Unless a listing is explicitly identified as a complete program, C++ snippets in this chapter are separate excerpts. They require #include <cute/tensor.hpp> and a surrounding function; use the linked complete oracle for a copyable translation unit and its full compile command. Repeated variable names in different excerpts are not instructions to concatenate them into one scope.

    The primary references are the pinned layout tutorial, layout algebra, and tensor tutorial.

    Before the algebra: a reproducible workspace¶

    The introductory path is 15 → 16 → 17 → 18 → 19. Continue through the intermediate copy/MMA/shared-memory/GEMM labs in 20–24, then the advanced pipeline, fusion, precision and measurement chapters in 25–29. You do not need to understand a CUTLASS builder before learning a coordinate map.

    Use a terminal in the book repository root. On the CUDA host, prepare the same pinned dependency used throughout this sequence:

    export CUTLASS_ROOT="$HOME/cutlass-v4.3.6"
bash tools/fetch_cutlass.sh "$CUTLASS_ROOT"
mkdir -p build/advanced

    The helper verifies v4.3.6 commit 1afc6d355b8cb992398f17beb4425702f1d57ddd. The CPU indexing workbook needs only Python’s standard library, so you can work through the arithmetic on a laptop before using the GPU host. The CuTe C++ exercises use actual CUTLASS/CUDA headers; their compilation is separate from the Python reference’s checks.

    2 — Shape says which coordinates; stride says where¶

    For a two-mode layout with shape (3,4) and stride (4,1), the address offset is

    offset(m,n) = 4m + n, for 0 ≤ m < 3, 0 ≤ n < 4.

    Coordinate row n=0 n=1 n=2 n=3
    m=0 0 1 2 3
    m=1 4 5 6 7
    m=2 8 9 10 11

    The explicit construction is:

    auto row_major = cute::make_layout(
    cute::make_shape(cute::Int<3>{}, cute::Int<4>{}),
    cute::make_stride(cute::Int<4>{}, cute::Int<1>{}));
auto offset = row_major(cute::make_coord(2, 3)); // 11

    Offsets are in the layout’s indexing units—normally elements when paired with a typed pointer—not automatically bytes. Multiply by sizeof(Element) when comparing with a byte-addressed PTX descriptor. make_layout(shape) defaults to a left-major compact layout; it is not a request for the row-major convention used above. Always print or enumerate a new layout before relying on a familiar name.

    A shape describes the intended logical domain; it is not a runtime bounds-checking wrapper. For shape (3,4), coordinate (3,0) is invalid even if applying the stride formula produces the integer offset 12. A larger backing allocation does not turn that coordinate into part of this logical tensor. Check coordinates before dereferencing, and retain the original extents when rounded tiles extend the view's coordinate envelope. Compile-time type compatibility and runtime coordinate validity are different checks.

    Int<4>{} carries the value in its type; int k = 4 carries a runtime value. Both can participate in a layout. Static information lets template code prove constraints and specialize indexing, but it also increases the variety of instantiated types. Make dimensions static because an instruction or algorithm needs that fact, not simply because static syntax looks faster.

    Compare row-major and column-major without changing the coordinates¶

    For the same shape (3,4), column-major stride (1,3) gives this table:

    Coordinate row n=0 n=1 n=2 n=3
    m=0 0 3 6 9
    m=1 1 4 7 10
    m=2 2 5 8 11

    Both layouts have 12 logical elements and the same largest offset, but most interior coordinates name different storage positions. At (1,2), row-major gives 6 and column-major gives 7. Testing only (0,0) and the last element would miss that difference. The words “row-major” refer to which mathematical coordinate changes contiguously; they do not follow from the order in which an author happened to list shape names.

    For a row-major batched tensor (L,M,N) with packed batches, offset(l,m,n)=l*M*N+m*N+n. With physical row length ld>=N and batch stride sb, it becomes l*sb+m*ld+n. A tensor’s mathematical shape therefore does not uniquely determine its storage. A framework view can have padding or noncompact strides without changing its logical dimensions.

    A transpose view swaps the coordinate interpretation and the corresponding shape/stride modes. It does not physically rearrange the allocation. On a rectangular 3×4 row-major matrix, a 4×3 transposed view uses stride (1,4): transposed coordinate (2,1) refers to original (1,2), offset 6. Keep the original allocation’s lifetime valid while any such view is used.

    Walk one coordinate all the way to bytes¶

    Construct both layouts explicitly, keeping coordinate names fixed:

    auto row_major = cute::make_layout(
    cute::make_shape(cute::Int<3>{}, cute::Int<4>{}),
    cute::make_stride(cute::Int<4>{}, cute::Int<1>{}));
auto column_major = cute::make_layout(
    cute::make_shape(cute::Int<3>{}, cute::Int<4>{}),
    cute::make_stride(cute::Int<1>{}, cute::Int<3>{}));
auto row_offset = row_major(cute::make_coord(1, 2));
auto column_offset = column_major(cute::make_coord(1, 2));
    1. The shape says that (1,2) is valid: row one is below three and column two is below four.
    2. Row-major stride (4,1) contributes 1×4 from the row and 2×1 from the column, totaling six elements.
    3. Column-major stride (1,3) contributes 1×1+2×3=7 elements. The logical coordinate is unchanged; only its address map differs.
    4. For FP16 storage, multiply by two bytes per element. The offsets become 12 and 14 bytes. From a hypothetical byte base 0x1000, those would be 0x100C and 0x100E; these illustrative addresses are not pointers to dereference.
    5. The layout object returns an offset. A tensor access uses that offset with its engine to read or write a value. Computing the offset alone has moved no data.

    Expected result: row_offset=6, column_offset=7. Check: enumerate an entire interior row rather than checking only the corners. Pitfall: calling (1,3) “row-major” while defining the first coordinate as a row reverses the convention; inspect what happens when the column increases by one.

    Keep the same mapping with runtime dimensions¶

    int rows = 3, columns = 4, leading_dimension = 4;
auto runtime_row = cute::make_layout(
    cute::make_shape(rows, columns),
    cute::make_stride(leading_dimension, cute::Int<1>{}));
auto offset = runtime_row(cute::make_coord(1, 2)); // 6
    1. The first mode's stride is the supplied physical row length leading_dimension, here four.
    2. The arithmetic remains 1×4+2=6.
    3. The dimensions now have runtime values; the type does not encode three and four as Int<3> and Int<4>.
    4. The last stride remains statically one, so the compiler still has useful static information. Static and dynamic facts can coexist.

    Check: reconstructing the layout with leading_dimension=8 and the same logical shape (3,4) changes this offset to ten; that describes padded storage. Changing the original C++ variable after construction does not automatically update an existing layout object. Pitfall: static dimensions do not promise that every later coordinate or address calculation disappears from generated code. Inspect the actual instruction and resource report before making a performance claim.

    Extend the calculation to a packed batch¶

    A row-major tensor with logical shape (L,M,N)=(2,3,4) has element strides (12,4,1):

    auto batches = cute::make_layout(
    cute::make_shape(
        cute::Int<2>{}, cute::Int<3>{}, cute::Int<4>{}),
    cute::make_stride(
        cute::Int<12>{}, cute::Int<4>{}, cute::Int<1>{}));
auto last = batches(cute::make_coord(1, 2, 3)); // 23

    First select batch one: 1×12=12. Then move two rows: 2×4=8. Finally move three columns: 3×1=3. The sum is 23 elements, or 46 bytes for FP16. The 24-element packed allocation ends at exactly that coordinate. Check: batch zero's last coordinate is offset 11, while batch one's first coordinate is 12. Pitfall: using the output tile size as a batch stride would overlap independent matrices.

    Read the storage picture as well as the formula¶

    The following concrete map distinguishes logical values from physical offsets. For shape (4,3), highlighted value 201 belongs to coordinate (2,1). Row-major strides (3,1) select offset seven; column-major strides (1,4) select offset six. Both strips contain the same logical data arranged for their respective layouts.

    3 — Size and storage span are different¶

    Now retain shape (3,4) but use stride (8,1). The three rows start at offsets 0, 8 and 16. There are 12 logical coordinates, yet the largest referenced offset is 19. For this positive-stride example, the storage span through the last referenced element is 20.

    • size(layout) describes the number of logical elements: 12.
    • cosize(layout) describes the codomain span used for storage sizing in this example: 20.
    • An external allocation may be larger still, for example to reserve a full padded row or several aligned stages.

    A broadcast layout can map several coordinates to one offset. That may be useful for reads; it does not give independent destinations for parallel writes. The coordinate domain, image, storage bounds and ownership are separate properties. Do not generalize the simple positive-stride span arithmetic to arbitrary composed/swizzled layouts without checking the corresponding contract.

    Ask the API for each quantity, then reconstruct it¶

    auto padded = cute::make_layout(
    cute::make_shape(cute::Int<3>{}, cute::Int<4>{}),
    cute::make_stride(cute::Int<8>{}, cute::Int<1>{}));
auto useful = cute::size(padded); // 12 logical coordinates
auto span =
    cute::cosize(padded); // 20 for this positive-stride layout
    1. Count coordinates: three rows times four columns gives 12.
    2. Find the greatest used offset: row two, column three gives 2×8+3=19.
    3. Include offset zero: storing through offset 19 needs 20 elements, not 19.
    4. Compare with a full-row allocation: 3×8=24 reserves four additional trailing positions. Those positions are allocated but not part of this view's image.

    Check/pitfall: neither size nor the number of values printed in a matrix proves that a separate allocation is large enough. These span calculations assume the positive-stride example; do not reuse them as a rule for arbitrary negative or overlapping layouts.

    Guided exercise. Keep three rows and four columns but use row stride ten. What are useful size and minimum span?

    Worked answer: useful size remains 12. The last referenced offset is 2×10+3=23, so minimum span is 24 elements; three complete padded rows would reserve 30.

    4 — Hierarchy is part of the meaning¶

    A layout may have nested shapes such as ((2,2),4). The first mode retains a factorization: two subcoordinates describe its four positions. This is useful when those factors correspond to lanes, values per lane, subtiles or an instruction atom. Flattening the shape can hide exactly the structure that a copy or MMA partition expects.

    coalesce simplifies compatible layout factors while preserving the mapping it represents. It does not move the tensor, erase data padding by copying, or preserve every original hierarchy boundary. When a later operation expects a particular mode structure, use the algebra’s mode/profile-aware forms and inspect the resulting shape.

    Retain the hierarchy while calculating an element¶

    auto hierarchy = cute::make_layout(
    cute::make_shape(
        cute::make_shape(cute::Int<2>{}, cute::Int<2>{}),
        cute::Int<4>{}),
    cute::make_stride(
        cute::make_stride(cute::Int<1>{}, cute::Int<2>{}),
        cute::Int<8>{}));
auto offset =
    hierarchy(cute::make_coord(cute::make_coord(1, 1), 2));
    1. The coordinate is ((a,b),c)=((1,1),2), matching the shape's nested profile.
    2. The inner contribution is 1×1+1×2=3.
    3. The outer contribution is 2×8=16, giving offset 19 elements.
    4. The inner tile contains four positions, while its repetitions start at offsets 0,8,16,24. A hierarchy can therefore retain both a useful factorization and real storage gaps.

    Expected result: offset 19; no data moves. Pitfall: replacing the profile with three unstructured indices can change the interface expected by the next partitioning operation, even if an independently constructed flat layout can reproduce the same arithmetic.

    Guided exercise. Locate ((0,1),3).

    Worked answer: 0×1+1×2+3×8=26 elements. It lies in the fourth outer region, not the third.

    5 — Composition is function composition¶

    If layout A maps an index to a storage offset and layout B maps a new coordinate to an index accepted by A, their composition maps x to A(B(x)). Order matters. This is a view transformation: no loads or stores occur merely because a composed layout was constructed.

    A simple scalar example makes the direction visible. Let A(i)=2i and B(j)=j+1 over a valid domain. Then A(B(j))=2j+2, while B(A(j))=2j+1. Real CuTe layouts must satisfy the algebra’s compatibility rules; this arithmetic analogy does not make every arbitrary affine function a valid Layout constructor.

    When debugging composition, enumerate the small domain on paper and compare three quantities: the input coordinate, its intermediate index, and its final offset. Then test the actual CuTe object. A type that compiles is not proof that the chosen mapping matches your matrix convention.

    Preview the real composition API¶

    auto outer = cute::make_layout(cute::Int<16>{}, cute::Int<2>{});
auto inner = cute::make_layout(cute::Int<4>{}, cute::Int<3>{});
auto selected = cute::composition(outer, inner);
    1. Choose x=2 in the inner layout's four-index domain.
    2. The inner map returns 3×2=6, a valid logical index in the outer layout's 16-index domain.
    3. The outer map returns 2×6=12 elements. Thus selected(2) describes physical offset 12.
    4. The intermediate index six and final offset twelve are not interchangeable. This constructs no data buffer and issues no memory operation.

    Guided exercise. What does x=3 select?

    Worked answer: inner index nine, then outer offset 18. Chapter 17 adds a physical memory strip and complete-domain checks for this exact construction. Reversing the argument order requires rechecking the intermediate domain, not merely exchanging labels.

    6 — Divide a layout into tiles¶

    A contiguous 12-element layout can be logically divided into tiles of four. The new coordinates are (within_tile, tile_number), with offsets within_tile + 4 * tile_number.

    Tile Four offsets
    0 0, 1, 2, 3
    1 4, 5, 6, 7
    2 8, 9, 10, 11 
    auto contiguous = cute::make_layout(cute::Int<12>{});
auto tiled = cute::logical_divide(contiguous, cute::Int<4>{});
auto offset = tiled(cute::make_coord(2, 1)); // 6

    logical_divide, zipped_divide and their multidimensional relatives organize tile and remainder modes differently. Learn the returned shape, not just the function name. A layout view does not allocate a shared-memory stage, issue TMA, or predicate out-of-bounds coordinates. A kernel still needs those operations and their synchronization protocol.

    Follow one divided coordinate without flattening it twice¶

    1. Choose logical length 12 and tile length four, as in the API call above.
    2. Tile number one starts at 1×4=4.
    3. Within-tile coordinate two adds two, so tiled(make_coord(2,1)) selects offset six.
    4. The corresponding original scalar coordinate is six. Calling the divided object with a guessed row-major flattened coordinate is unnecessary; keep (within,tile) explicit until its convention is understood.

    Guided exercise. Which pair selects the last original element, offset 11?

    Worked answer: (within,tile)=(3,2), because 3+4×2=11. Pair (4,1) is outside the tile's four-position logical domain even though a naive arithmetic expression could produce an integer.

    7 — Tensors, slices and thread/value partitions¶

    A CuTe tensor combines a data engine with a layout. A pointer-backed view over global memory differs from an owning register tensor even when their logical shapes match. Slicing chooses coordinates/modes; local_tile selects a tile; a tiled copy or tiled MMA assigns parts of a tensor to participating threads.

    The useful debugging chain is:

    matrix coordinates → tile coordinates → thread/value coordinates → element offset → byte address.

    For a load, ask whether every needed element is covered. For a store, also ask whether two threads can target the same address. For MMA, ask whether the fragment matches the exact atom and operand convention. The register layouts from Chapters 6–7 are not replaced by a generic “row-major register array” merely because CuTe performs the partitioning.

    When reading a TiledCopy or TiledMMA, locate its atom, thread layout and value layout. Then inspect the per-thread slice and its partition functions. A partition describes ownership; the actual copy/MMA call performs work. NVIDIA’s copy/MMA atom tutorial connects these layers.

    Attach a view only after specifying its storage¶

    // ptr names an existing, suitably accessible float allocation.
auto view = cute::make_tensor(
    cute::make_gmem_ptr(ptr),
    cute::make_layout(cute::make_shape(3, 4),
                      cute::make_stride(4, cute::Int<1>{})));
auto second_row = view(1, cute::_);
    1. The engine retains a pointer to existing storage; the layout retains the address map.
    2. Fixing row one adds four elements to the view's base.
    3. Row-local coordinate two would select original (1,2), offset six.
    4. This view still references the original allocation. It does not initialize it, copy it or extend its lifetime; GPU memory is not made CPU-readable by constructing a host-side view.

    Guided exercise. With physical row stride eight instead, what does the same logical selection name?

    Worked answer: offset 1×8+2=10 elements. The slice remains four logical columns wide, but its base offset changes. Chapter 18 supplies the complete value/offset walkthrough and explains the host/device access boundary.

    8 — Swizzles are layout transforms, not faster copies¶

    A shared-memory swizzle changes the mapping between logical coordinates and shared addresses. It can improve bank behavior for a particular access pattern. It must also agree with the TMA and WGMMA layout descriptions. A swizzle applied only to the producer or only to the consumer scrambles the computation.

    Check the base alignment, pattern start, tile shape and descriptor fields from Chapters 4 and 6. A swizzled allocation needs the correct storage span and alignment; size alone is not a universal shared-memory allocation recipe. Start with a supported CUTLASS builder layout before inventing a custom composition.

    Derive a four-word swizzle without a performance claim¶

    auto square = cute::make_layout(
    cute::make_shape(cute::Int<2>{}, cute::Int<2>{}),
    cute::make_stride(cute::Int<2>{}, cute::Int<1>{}));
auto permuted = cute::composition(cute::Swizzle<1, 0, 1>{}, square);
    1. The ordinary logical grid references word offsets [[0,1],[2,3]].
    2. This swizzle XORs index bit one into bit zero. Offsets zero and one keep a zero source bit, so they stay zero and one.
    3. Offset two, binary 10, becomes 11 (three); offset three becomes 10 (two).
    4. The new grid references [[0,1],[3,2]]. The same four word locations exist, but the last two logical coordinates exchange their physical interpretation.

    Guided exercise. If a producer writes using the original layout and a consumer reads using only the new layout, does the consumer obtain the same matrix?

    Worked answer: generally no: logical (1,0) now reads word three instead of word two. Both sides must agree on the physical mapping, or an explicit transformation must connect them. Bijection alone also does not prove improved bank behavior; Chapter 22 studies that separate question.

    9 — Run the coordinate oracle¶

    The complete cute_layouts.cu enumerates both matrix mappings and the divided one-dimensional layout. It launches no GPU kernel. We compile it with the pinned CUDA/CUTLASS toolchain so that its C++ header dependencies match the later GEMM.

    nvcc -std=c++17 -O2 --expt-relaxed-constexpr \
  -I "$CUTLASS_ROOT/include" \
  docs/examples/advanced/cute_layouts.cu -o build/advanced/cute_layouts
./build/advanced/cute_layouts

    Create build/advanced and set CUTLASS_ROOT using the workspace steps above. Expected checks are the row-major coordinate table above, size(padded)=12, cosize(padded)=20, and LAYOUT PASS with zero errors. These are specifications to verify, not a captured run transcript. The separate advanced collector retains actual output, source identities and system information for its executions.

    Self-check: does a new layout transpose the allocation?

    You change a pointer-backed tensor view’s strides. Have you transposed the bytes?

    Answer: No. You changed which bytes each logical coordinate names. A physical transpose requires reads and writes into the intended destination layout, with valid ownership and synchronization.

    Self-check: how many elements do you allocate?

    Shape (3,4), stride (8,1): is a 12-element buffer enough?

    Answer: No. Offset 19 is referenced, so this example needs a span of at least 20 elements. Additional padding/alignment may require a larger allocation.

    Tested source SHA-256: 39e99111ba0dd6a48ecb812bd9ce6afe918e557407c8160a6dd8f8b1c530ab3f. Exact source · System information · Workshop results.

    The listing below matches the tested source. Its presentation is formatted at build time; downloads retain the captured bytes.

    // CuTe coordinate checks. No GPU kernel is launched by this program.
#include <cute/tensor.hpp>
#include <cstdio>
#include <stdexcept>
using namespace cute;

int main() {
    auto row = make_layout(make_shape(Int<3>{}, Int<4>{}),
                           make_stride(Int<4>{}, Int<1>{}));
    auto padded = make_layout(make_shape(Int<3>{}, Int<4>{}),
                              make_stride(Int<8>{}, Int<1>{}));
    int errors = 0;
    for (int m = 0; m < 3; ++m) {
        for (int n = 0; n < 4; ++n) {
            const int offset = row(make_coord(m, n));
            errors += offset != 4 * m + n;
            errors += padded(make_coord(m, n)) != 8 * m + n;
            std::printf("%2d%s", offset, n == 3 ? "\n" : " ");
        }
    }
    errors += int(size(row)) != 12 || int(cosize(row)) != 12;
    errors += int(size(padded)) != 12 || int(cosize(padded)) != 20;
    auto contiguous = make_layout(Int<12>{});
    auto divided = logical_divide(contiguous, Int<4>{});
    for (int tile = 0; tile < 3; ++tile)
        for (int within = 0; within < 4; ++within)
            errors += divided(make_coord(within, tile)) !=
                      within + 4 * tile;
    std::printf("size(padded)=%d cosize(padded)=%d\n",
                int(size(padded)),
                int(cosize(padded)));
    std::printf(
        "%s: 24 matrix coordinates, 12 tile coordinates; errors=%d\n",
        errors ? "LAYOUT FAIL" : "LAYOUT PASS",
        errors);
    return errors ? 1 : 0;
}

    Summary¶

    • A layout maps logical coordinates to offsets; its shape does not determine physical storage without strides and an explicit coordinate convention.

    • Views, coalescing and composition do not move values. Allocation bounds, ownership and actual copy/MMA operations remain separate responsibilities.

    • Use the pinned workspace and small coordinate oracles before progressing to hierarchical algebra and tensor views.
